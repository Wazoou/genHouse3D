# Decisions

Choices that the project brief leaves open, or where the implementation departs from it.

| Date | Decision | Reason |
|---|---|---|
| 2026-11-09 | Main dataset: **Swiss Dwellings v3.0.0** (Zenodo, CC BY 4.0), one plan per apartment, instead of Modified Swiss Dwellings (MSD). | MSD plans are whole building floors (20 to 70 rooms per graph in the official usage notebook), which the 4 to 10 room filter would reject almost entirely. Swiss Dwellings is MSD's parent dataset and carries apartment, building and site identifiers, metric geometry, doors and windows. CC BY 4.0 allows publishing derived samples and model weights with attribution. |
| 2026-11-09 | RPLAN stays optional. The adapter layer (`housegen.data.build.ADAPTERS`) takes a second dataset without touching the rest. | Access is by request form, for non-commercial research, with redistribution forbidden; the request had not been sent when the project started. |
| 2026-11-09 | ResPlan not used. | Conflicting licence statements (CC BY 4.0 on GitHub, CC BY-NC-SA 4.0 in its Kaggle metadata), undisclosed source platforms, no building identifier for a leakage-free split. |
| 2026-11-09 | **Fixed metric grid**: 256 x 256 units of 10 cm (25.6 m canvas), plan centred. The brief asks for a scale relative to each plan's bounding box. | With a per-plan scale, a generated plan has no size in metres: the area checks of the post-processing and the 3D extrusion would need a guessed scale. A fixed scale makes the model learn real sizes. 99.9 % of converted apartments fit in the canvas. |
| 2026-11-09 | **Rooms share edges** (planar partition); walls have no thickness in the unified format. Raw room outlines are net areas separated by the wall thickness, so the adapter closes the gaps onto the wall centre line. | The 3D pipeline rebuilds walls with configured thicknesses from room edges, and adjacency / overlap checks become exact on the integer grid. |
| 2026-11-09 | Plans are **rectilinear**: apartments with a slanted or curved wall are rejected (9,738 of 44,957). | The model snaps corners to the grid to get straight, aligned walls; slanted walls would need another representation. |
| 2026-11-09 | Doors are stored as a **segment on the wall** (two end points) rather than a small rectangle. | The wall has no thickness in the format; the 3D pipeline gives the opening its depth. |
| 2026-11-09 | Room connections have two kinds: `door` and `open` (rooms touching without a wall). | Open kitchens and corridors opening onto the living room are frequent (about one per plan) and the demo exposes "open kitchen". |
| 2026-11-09 | Type table: the generic `ROOM` label maps to `bedroom`; when an apartment has no annotated living room, its largest `ROOM` becomes `living` (flagged in `meta.living_inferred`). `LOGGIA` and `TERRACE` map to `balcony`. No `entrance` type: the entrance is the room carrying the entrance door. | The dataset labels most habitable rooms `ROOM`. MSD maps `ROOM` to bedroom as well. The share of inferred living rooms is reported in `reports/data_report.md`. |
| 2026-11-09 | Split **by site**, not by building. | A site groups the buildings of one development, which often repeat the same layouts. |
| 2026-11-09 | Duplicates are removed up to translation, quarter turns and mirroring, before the split. | Apartments are stacked on identical floors and mirrored around staircases; training will use the same symmetries as augmentation. Leaving them in would inflate the dataset and blur the novelty metric. |
| 2026-11-09 | No pandas: the raw CSV is streamed with the standard `csv` module. | Windows application control blocks the pandas DLL on the development machine; one dependency less on Kaggle and Spaces too. |
| 2026-11-09 | The working directory is the repository root (GitHub: `Wazoou/genHouse3D`), package name `housegen`. | Simplest layout. |
| 2026-11-09 | Windows are not stored in the unified format. | The brief places windows by rules in the 3D step. The raw windows stay available in the source file if the rules need calibrating. |
| 2026-11-11 | **Hip roof: own straight skeleton**, for rectilinear footprints, instead of a library (`housegen.geometry3d.roof`). | The brief asks for a Python straight-skeleton library. None of the pure-Python ones (`polyskel`, `bpypolyskel`) nor `scikit-geometry` is published on PyPI, and the CGAL binding that is (`compas_cgal`) ships a DLL that Windows application control blocks on the development machine. Since every plan is rectilinear on a grid, the skeleton is obtained exactly from shapely's mitred inward offsets, sliced at the events. A test checks the roof height against a closed form (L-infinity distance to the eaves). Non-rectilinear footprints fall back to the flat roof. |
| 2026-11-11 | Walls are built as **horizontal slices** (wall footprint minus the openings crossing each slice), each slice a watertight prism. No 3D boolean library. | Only shapely 2D operations are needed, which are exact enough and already a dependency. "Watertight" is therefore checked per body, not on the union. |
| 2026-11-11 | Triangulation by `shapely.constrained_delaunay_triangles`; `trimesh` is used for mesh checks and GLB export only. | Avoids extra compiled dependencies (earcut, triangle, manifold) that the application control policy might block. |
| 2026-11-11 | **Own software renderer** (numpy z-buffer, orthographic, shadow map) for the gallery, instead of pyrender or Blender. | Blender is not installed. pyrender needs an OpenGL context and pins PyOpenGL 3.1.0; it was not tried, a dependency-free renderer that also runs on CI, Kaggle and a CPU Space was the simpler option. |
| 2026-11-11 | Balconies are outdoor: floor slab and railing, no walls, no roof. A room open onto a balcony gets a doorway in the outer wall. | They are not part of the heated footprint; roofing them would distort the house shape. |
| 2026-11-11 | Gable roof only when the footprint fills at least 85 % of its bounding box; otherwise the hip roof is built and the fallback is reported. The gable roof covers the bounding box. | "Roughly rectangular" needed a threshold; the rate of fallbacks is measured in `reports/results/roof_stats_real.csv`. |
| 2026-11-11 | Door openings use the configured widths (0.9 m, entrance 1.0 m) centred on the plan's door, never wider than the plan's door segment. Window tops are capped 15 cm under the ceiling. | Keeps openings inside the wall piece that carries them and leaves a lintel. |
| 2026-11-11 | PyTorch is an optional extra: `cu126` (local GPU, CUDA 12.6) or `cpu` (CI). Kaggle uses its preinstalled PyTorch. | The data and 3D pipelines do not need it; CI should not download CUDA wheels. CUDA 12.6 builds support the RTX 2070; the CUDA 13 builds were not tried. |
| 2026-11-11 | **Compatibility** is the edit distance between the requested graph and the graph the plan *realises*: a requested connection counts as realised when the two rooms share a wall piece of at least 0.5 m (a door is placed there). Unit costs for rooms, room types and connections; the connection kind (door / open) is ignored. Exact branch and bound written for these small graphs, checked against networkx. | Rooms that are adjacent without being connected are legitimate (a wall without a door), so plain adjacency cannot be compared with the request. Real plans score 0 after their doors are stripped and re-derived, which is the sanity check asked by the brief. networkx's own solver was too slow for thousands of pairs. |
| 2026-11-11 | **Layout similarity** (diversity, novelty): share of occupied cells where two plans agree on the room type, on 64 x 64 maps of 0.4 m cells centred on each plan. Novelty takes the maximum over the eight symmetries and over all training plans (exact search). A plan at 0.9 or more is counted as a copy. | A type-aware IoU that is cheap enough to compare every generated plan with every training plan. The 0.9 threshold is a convention; the full histogram is reported next to it. |
| 2026-11-11 | **FID** on fixed-style renders *without doors*, 256 px, Inception pool3 features from `pytorch-fid`; the Fréchet distance itself is computed with numpy (eigenvalues), not scipy. | Raw model output has no doors, so both sides are rendered without them. Fewer compiled dependencies to load. |
| 2026-11-11 | **Validity** thresholds on room areas sit just under the 0.5th percentile of the training rooms (6 m² for bedrooms as in the brief). | A threshold was needed per type; real test plans are scored too, so the share of real plans it rejects is visible. |
| 2026-11-11 | **B0** shortlists 30 training graphs by a cheap signature (rooms per type, connections per pair of types) and re-ranks them by exact edit distance; it returns the 5 closest plans. | An exact search over 10,000 training graphs for each test graph is too slow; the shortlist is documented rather than hidden. |
| 2026-11-22 | **Model code written from the HouseDiffusion paper, not adapted from its repository.** | The official code is licensed for non-commercial research only (GPL v3 terms). The paper is cited in the README and in the docstrings. |
| 2026-11-22 | Relational attention links the corners of **rooms connected in the graph** (door or open), instead of rooms and door components as in HouseDiffusion. | Doors are not generated: they are placed on shared walls afterwards (`postprocess.attach_doors`). The kind of connection is not given to the model; it only matters for wall placement in 3D. |
| 2026-11-22 | Timestep through **adaLN-Zero** (DiT) in every layer; coordinates through Fourier features of the corner and of the vector to the next corner of its room. | adaLN-Zero is a standard, stable way to condition every layer; the edge vector stands in for HouseDiffusion's points sampled along the wall. |
| 2026-11-22 | Token order: rings counter-clockwise from their lowest-then-leftmost corner. Augmentation: the 8 symmetries of the square (precomputed) and random room identities among 16 slots. | A canonical order gives every token a well-defined target; both augmentations are tensor operations on the GPU, so no data-loader workers are needed (simplest on Windows). |
| 2026-11-22 | **Deterministic training stream**: batch `m`, its augmentation, timesteps and noise come from a generator seeded by `(seed, m)`; the batch order is a function of `(seed, epoch)`. | A resumed run continues exactly like an uninterrupted one without saving any sampler state (tested bit for bit on CPU). The global random states are saved in checkpoints anyway, as the brief asks. |
| 2026-11-22 | No `torch.compile`, no data-loader workers, CSV logs only (no TensorBoard). | Fewer moving parts on Windows; CSV is enough for the curves in the reports. |
| 2026-11-22 | The main model is trained **on the local RTX 2070** (fp16, about 1 h 30 for 60,000 steps of 256 plans) rather than on Kaggle. The Kaggle notebook and `make kaggle-bundle` are ready but unused so far. | The model is small (10.6 M parameters, 2.5 GB of GPU memory); Kaggle needs the user's account. The brief's 24 GPU-hour budget is far from reached. |
| 2026-11-22 | Clean-up thresholds chosen on **300 validation graphs** with the 20,000-step snapshot (DDIM 100 steps), never on the test split. Gap closing: 0.4 m: 52.7 % valid / 45.0 % graph respected; 0.6 m: 57.0 / 49.3; **0.8 m: 60.3 / 53.3**; 1.0 m: 61.7 / 55.3. Allowing 0.8 m of overlap instead of 0.4 m lowers validity by 10 to 13 points. Kept: 0.8 m gaps, 0.4 m overlaps. | 1.0 m is marginally better but stretches rooms further; the effect of clean-up is always reported next to the raw output. |
| 2026-11-22 | Gradio cannot be imported on the development machine (application control blocks its pandas dependency), so the demo is split: `housegen.demo` (tested locally) and a thin `app/app.py`, whose UI is built and exercised by a CI job on Linux. | Keeps every line of logic testable here. |
